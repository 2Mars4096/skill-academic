# Pushback Rules

Use this when the user has an interesting idea that is still too vague, too broad, or too fragile.

Push back in a way that narrows the project. Do not just say the idea is weak.

## Canonical Pushback Types

### 1. Question Pushback

Use when the user has named a topic, not a question.

Ask:

- What exact outcome do you want to explain?
- Relative to what comparison?
- For which unit?

### 2. Contribution Pushback

Use when the project sounds familiar or derivative.

Ask:

- Which paper is the closest benchmark?
- What exact margin is new here: setting, data, mechanism, or interpretation?
- Why is that margin important rather than cosmetic?

### 3. Data Pushback

Use when the user says the data should exist, but cannot name the source or construction path.

Ask:

- Where would the raw data come from?
- What is the hardest variable to construct?
- What is the fallback if the key variable is unavailable?

### 4. Design Pushback

Use when the causal or evidentiary logic is weak.

Ask:

- What is the actual comparison generating evidence?
- Why would that comparison isolate the effect rather than selection or confounding?
- If that logic fails, should the project be reframed as descriptive?

### 5. Scope Pushback

Use when the user is forcing several projects into one proposal.

Ask:

- What is the one result the paper must deliver?
- Which questions should move to the parking lot?

## Preferred Tone

- direct
- specific
- constructive
- non-performative

Bad pushback:

- `This is too broad.`
- `The idea is not identified.`

Better pushback:

- `The topic is interesting, but it is still a domain rather than a question. The narrowest viable version is whether [variation] changes [outcome] for [unit].`
- `Right now the mechanism is a story, not an empirical object. Either add a proxy test for the channel or downgrade the claim.`

## Escalation Rule

If the same weakness survives two rounds, stop adding prose and force a decision:

- sharpen
- downgrade
- pivot
- park
